# Project: lazyboards

Go (BubbleTea) TUI application. Single project.
GitHub Issues for tracking. GitHub for code and PRs.

## Critical Rules
- ALWAYS read relevant `.claude/rules/` files before working on any layer.
- Test-first: write tests that assert behavior, not implementation details.
- No PR should exceed ~300 lines. Split into stacked PRs if larger.
- Use git worktrees for all feature work. Never modify code in main worktree.
- The help modal (`?`) and the status-bar hints are generated from the active `*keymap.Keymap` registry (`keymap_help.go`'s `buildHelpContent`/`helpModeSections`, `keymap_dispatch.go`'s `registryHints`) -- never hand-edit help/hint text or add a per-key wording table. When adding a new mode, add one curated entry (title + `keymap.Mode` + optional `openedBy`) to `helpModeSections` in `keymap_help.go`; every row beneath it is derived automatically from `b.keys.Entries(mode, column)`, and a drift test fails if a mode is added to `keymap.Modes()` without one. When adding a new keybinding, add it to the relevant default `Table` in `internal/keymap` (its catalogued `Desc` becomes the help row's label) -- and update the README Keybindings section.
- When changing how a documented UI element renders (status glyphs, badges, colors, indicators), update its description in README.md — changes to visual meaning must stay synchronized with documentation.
- `keymaps:` is the only config syntax for key bindings. The pre-0.73 top-level `actions:` and per-column `columns[].actions:` blocks are gone: `internal/config`'s `stampOrderAndRejectLegacy` (`config.go`) rejects either at load time (and in `Save`) with an error naming the file and key, presence-based on the raw YAML key whatever its value. Never reintroduce a translation shim, a `Config.Actions`/`ColumnConfig.Actions` field, or a doc example in the old shape.
- Keybinding case convention: every key surface (normal mode, the detail panel, sub-panels/modals, and every text/confirm mode) dispatches through the `internal/keymap` registry (see `docs/keymaps.md`) — a new behavior is added as a catalogued command id (`internal/keymap/command_*.go`) with a default binding (`internal/keymap/defaults_*.go`), never as a hardcoded `switch msg.String()` case. Any key, uppercase or lowercase, may bind a built-in command or an inline (custom) action; a user binding always wins over a default, and rebinding a built-in's key means its old key stops working unless separately re-bound. `ctrl+c` is never bindable: `keymap.Keymap.Lookup` unconditionally short-circuits it to `app.quit` before consulting any table, and config load rejects binding *or* unbinding it anywhere, in any mode or column. Uppercase is **no longer** globally reserved for user custom actions (#502): the shipped normal-mode defaults now follow neovim-style mnemonics — lowercase keys are the primary, single-purpose commands (`n e c o r p x d a f l j k q s`, etc.), `g` is a go-prefix for two-key "go to X" navigation sequences (`g a` nav.agent, `g r` nav.reference), and `D`/`P`/`A`/`G` ship as the wider-scope uppercase siblings of their lowercase counterpart (`D`ispatch vs. `d`elete, `P`R list vs. `p`R open, `A`gents list vs. `g a` go-to-agent, `G`it menu). Uppercase still denotes scoped sub-commands inside sub-panels/modals too (e.g. Git Menu `P` = Push, `S` = Stash pop) — those are a separate namespace (`keymap.ModeGitPanel`, etc.), independent of the normal-mode table. When adding a new top-level built-in, don't assume a case-based namespace is free — pick any free key (either case, checking the current default tables in `internal/keymap/defaults_board.go` and the README's Keybindings section) rather than defaulting to lowercase or assuming uppercase is reserved. When adding a new mode or command id, also update its capability metadata in the same change — `internal/keymap/mode.go`'s `textInputModes`/`inlineActionModes`/`sequenceModes` membership, and, for a new universal command, `capability.go`'s `universalCommands`/`buildCommandModeIndex` widenings — plus the `docs/keymaps.md#mode-capability-matrix` block; never accept a binding the mode's dispatch seam cannot reach — `internal/config`'s `validateModeCapabilities`/`validateSequenceCapability` must reject it at load time, not silently no-op at runtime.
- Any new config construct that executes a command must be reachable by the trust model's local-shell-sink gate in the same change. `internal/config/trust_strip.go`'s `stripShellBindings` strips a local-origin binding only when `Action.Type == "shell"`; a new *type* value that shells out is a silent trust bypass unless that gate is widened with it. Prefer a modifier on the existing `shell` type — that is exactly why `terminal: true` (#623, the `tea.ExecProcess` foreground path) and `window:`/`cwd:`/`focus:` (#624, the `action.TmuxNewWindow`/`WithDir` path) are plain fields and not a `type: exec`/`type: tmux`, and why `sameShellAction` compares `Action` by whole-struct value so a newly added field is covered fail-safe rather than silently ignored. See `docs/trust-model.md`.
- A template-bearing `config.Action`/`keymap.Action` field (one whose value can contain `{var}` placeholders) must be added to `Action.Template()` in the same change, never read as a bare `a.URL + a.Command` concatenation at a new call site. `Template()` is the single accessor every "does this action reference variable X?" site consumes -- scope inference and the board/card variable restrictions (`validateActionValue`), the `{comment}` Alt-overload scan and the on-demand `{pr_worktree}` lookup (`action_dispatch.go`), and the alt-comment shadow check (`keymap_validate.go`). A field missed by one of them lets a board-scope action smuggle `{number}` in through the missed field, or leaves `{pr_worktree}` expanding to an empty path at dispatch.
- When a new feature consumes a state struct that already has an established rendering or handling precedence elsewhere in the codebase (in an earlier feature or related component), the new consumer must implement the FULL precedence, not just the happy path and obvious errors. Write tests that verify every state the existing precedence distinguishes — a missing intermediate state (e.g., "daemon not running" vs. "healthy running") will silently render incorrectly and undermine the feature's purpose.
- cenci integration placement rule: two things are built-in code paths — (1) stateful reads of live cenci/cenci-watch state that the app continuously displays (agent status badges, the dispatch modal's Loop line, the status-bar dispatch segment), and (2) the mutating cenci triggers scoped to the dispatch modal (enroll/unenroll, dispatch-once, and loop on/off), each fired by a modal key against cenci's own fleet/repo state. Fleet-wide, persistent mutations (loop on/off) must go through a two-step confirm in both directions and name their blast radius ("all enrolled repos"), mirroring the close-confirm flow (#433). Everything else that imperatively shells out to cenci with app-specific templating stays a user-configured custom action — don't build those in as code paths.
- When a refactor removes all production call sites of a function, delete it from production code — don't keep it alive because tests still call it. Migrate test coverage to the surviving building blocks instead.
- Before inlining or removing a single-call-site function during refactor, consult the plan's Assumptions and Architectural Context sections — it may be a pre-designed API surface for a concretely-scoped follow-on ticket in the same stack, not a premature abstraction.
- When a feature needs to reference a fixed, app-wide entity (e.g., lazyboards' own GitHub repo for update checks), don't reuse Board fields like `repoOwner`/`repoName` which are semantically the user's configured tracked repo. Create separate, explicitly-named constants to prevent confusion and misuse.
- When a spec defines precedence across multiple orthogonal axes (e.g., layer: user vs. default, scope: column vs. mode), state the explicit combined order across all combinations — not just each axis independently. A spec stating "user merges over default" and separately "column wins on conflict" doesn't specify whether `default-column` overrides `user-mode`. Implementation will encode one axis as the outer loop; if unspecified, this silent choice risks fail-open bugs (e.g., default bindings overriding user unbinds).
- When refactoring dispatch logic to centralize (keymaps, handler consolidation), diff the new dispatcher against the established pattern and replicate all guards: type-checks (`Binding.Kind`), state-precedence conditions (`OutcomePending`), negative branches. Omitted guards create fail-closed-by-accident implicit invariants that silently break if the guarded type evolves.
- When adding new production or test files, add corresponding rows to the File Structure tables in `AGENTS.md` — keep file-level documentation synchronized with actual structure.
