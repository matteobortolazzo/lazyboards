# Keymap and Config Layer Conventions

Rules for `internal/keymap`, `internal/config`, and related config-handling code.

See also [`keymaps.md`](keymaps.md) for the registry architecture and config
schema reference (layers, resolution/precedence, load-time validation, how to
add a command id) — this file is the append-only lessons log for the same
subsystem.

## Rules

- Column name matching in config (e.g. merging `keymaps.columns` entries) must use case-insensitive lookup to align with `internal/keymap`'s established convention (`mergeKeymaps`'s `globalColumnsByLower`, `lowercaseColumnNames`). Use `strings.ToLower()` when storing or looking up column names, and mirror collision-detection logic (rejecting raw-name pairs that lowercase to the same value). This prevents silent duplicate-column errors when entries mix different case variants of the same column name.

- When building a modal's hint-bar from the registry, only advertise bindings that the dispatcher can actually resolve. If a modal has no pending-sequence/which-key machinery to resolve multi-key sequences, exclude multi-key sequences from its hints—a hint for an unresolvable key-combo creates a hint/dispatch mismatch where users see an advertised key that silently no-ops if pressed.

- When testing a remap of a command in a mode where `Mode.ConsumesPrintableRunes() == true` (delete, close_confirm, label_confirm, and potentially others per #539/#491 migration), the test must remap to a **named key** (`"tab"`, `"enter"`, `"esc"`, etc.), never a **bare printable rune** (`"c"`, `"y"`, etc.). Config validation (keymap_semantic_validate.go's `validatePrintableRuneBindings`) forbids bare printable-rune bindings in such modes at load time — a mode's textinput handler swallows every literal rune before any lookup could see it. A test using `boardWithOverrideKeymap` (or other raw-keymap construction) bypasses this validation, creating an unreachable production state. A GREEN-phase implementer who then "fixes" code to satisfy such a test will silently weaken the defense-in-depth guard in `textBinding` (keymap_text.go) that protects even hypothetically-unvalidated keymaps.

- When a new hint-derivation helper layers on an existing filtering helper, ensure the new selection logic doesn't depend on information the upstream filter discards. For example, `glyphHintKey` (arrow-glyph preference) composes with `commandHintKeys` (which suppresses arrow aliases when non-alias keys exist), creating silent data-loss when a keymap has both keys bound to the same command. Test composition against all existing consumers' real keymap data, not just the new caller — the interaction only surfaces with specific binding combinations.

- When computing a label or display value derived from registry data (e.g., longest common `Desc` prefix for a command family's range collapse in help generation), guard against empty or falsy results — a missing check causes silent rendering failures where the UI displays a blank label instead of falling back to the safe default. For numeric-suffix family collapse, if `commonPrefixLabel` returns `""`, decline the collapse and render each member via the per-command fallback instead of a range row with a blank label. Write a test with synthetic catalogue entries that share no common prefix to pin this edge case.

- Cross-references in `internal/keymap` comments (production *and* `_test.go`) cite **symbols and command ids, never `file.go:<line>`** — a bare file name in parentheses is the only locator allowed (`handleGitPanelKey (mode_handlers.go)`). Line numbers rot on the first unrelated edit and silently mislead the next refactor. For the same reason, describe a binding in prose by its command id with the shipped default in parentheses — `nav.reference` (default `g r`) — never as a bare key literal, since a user binding can move any default (a table's own literal map keys are data, not prose, and stay). And don't cite a symbol you are deleting: when a refactor removes the var a comment was transcribed from, **delete** the provenance clause rather than repointing it — the live guarantee that wording stays in sync is the drift tests (`keymap_help_test.go`, `keymap_panels_test.go`, `git_keymap_defaults_test.go`), not prose. Design rationale (why a `Desc` reads the way it does) is not provenance and survives.

- #583's repo-wide audit for hardcoded user-visible key instructions found exactly two literal-key hints with no catalogued command behind them: `seqHints`' trailing `esc` (`keymap_dispatch.go`, the pending-sequence which-key bar) and `refHints`' trailing `esc` (`references.go`, the reference-navigation prompt). Both stay hard-wired and are documented as intentional exceptions rather than growing a new catalogued cancel command — `handlePendingSeqKey`/`handlePendingRefKey` branch on `tea.KeyEsc` directly, the exact same class of hard-wire as `Lookup`'s `ctrl+c` short-circuit (`internal/keymap/lookup.go`), which is the precedent both mirror: a fixed, uncatalogued key that every mode must honor regardless of remapping, so there is nothing for a user binding to override. Every other user-visible instruction site (delete prompts, Help Usage, the filter no-matches warning) derives its key from the registry instead. When adding a new instruction site, only reach for a hard-wired literal if it mirrors this same "no catalogued command, dispatcher checks the raw key type directly" shape — otherwise resolve it through `commandHintKeys`/`commandInstructionKey`/`textHintKey` like every other site in the codebase.

- Normal-mode instruction helpers (`commandInstructionKey`, `keymap_dispatch.go`) must **not** filter entries through `singleKeyEntries` (`keymap_text.go`) the way text/confirm-mode instruction helpers (`textHintKey`) do. `singleKeyEntries` drops multi-key sequences because text/confirm modes' `textBinding` seam can only dispatch a single-key-exact lookup — but normal mode's pending-sequence which-key flow (`handlePendingSeqKey`) *can* dispatch a multi-key sequence, so filtering them out of a normal-mode instruction (e.g. the filter no-matches warning's `board.filter` key) would silently hide a truthful `g f`-style remap. Read the resolved entries for the mode actually dispatching the instruction's command, not a filter borrowed from a different mode's dispatch constraints.

- #582: a column overlay's *effective* action table (`b.keys.Entries(mode, column)`) must be read **unfiltered** when deciding whether a global action hint still applies to the active column — never pre-filtered down to `BindingAction` entries first (`actionOnlyEntries`) before overlaying. `Keymap.Resolve` always merges a column's overlay onto the global table, so `BindingUnbound`/`BindingCommand` column entries are present in that effective table as suppression markers for the corresponding global action; a helper that filters them out before comparing can no longer tell "column doesn't mention this key" (fall through to global) apart from "column explicitly un-mapped this key from being an action" (suppress the global hint) — it silently falls through to the global action either way, keeping a hint alive for a key that no longer dispatches it. `effectiveActionEntries` (`keymap_dispatch.go`) is the reference implementation: build the override map from the unfiltered effective table, keep global order for keys still resolving to a `BindingAction`, and only append column-only actions from the filtered/ordered subset.

- #582: any hint-bar builder that resolves a command's key via a helper that can return `""` (`panelHintKey` and its siblings) must never construct `Hint{Desc: ...}` unconditionally around that lookup — append the hint only when the resolved key is non-empty (`appendPanelHint`, `keymap_panels.go`). Unbinding every key for a panel command must remove that command's hint entirely, not render a dead `: Close`/`: Run`/`: Enroll` affordance with a blank key. This is the same "hint must imply the key dispatches" invariant `docs/view-state-consistency.md` states for the general case, restated here because the panel-mode builders (`gitPanelHints`, `dispatchModalHints`, `helpHints`) are exactly the place a `key != ""` guard is easy to forget when adding a new hint line — `errorHints` (`keymap_panels.go`) is the one deliberate exception: it stays on `builtinHints`, which already guards for empty `commandHintKeys()` results structurally, so it never needed the same guard bolted on.
