# YAML Parsing with yaml.v3

Custom `UnmarshalYAML` implementations in the `internal/config` package.

## Rules

- When implementing `UnmarshalYAML` on a type that could receive a `!!null` scalar node, explicitly check `valueNode.Tag == "!!null"` **before** calling `node.Decode(&target)`. The yaml.v3 library short-circuits `Decode` for null nodes, invoking the zero-value path directly and bypassing your custom `UnmarshalYAML` handler entirely. Place the null-tag check in the caller (e.g., `parseKeymapTable`) as the primary guard; also add a secondary null-tag check inside `UnmarshalYAML` itself as defense-in-depth for other decode paths that might reach it differently.
- Never use a raw-node walk (iterating `yaml.Node.Content` by hand and checking literal `ValueNode.Value` strings) to make a security-relevant decision (provenance/trust gate, format validation, origin detection, etc.) when a full `yaml.v3` decode of the same input is also happening in the same code path. A raw-node walk and yaml.v3's full generic map decoder can diverge on YAML features like merge keys (`<<: *anchor`), aliases (`*anchor`), and anchor resolution — the decoder expands these but a hand-rolled walk does not. This means a security gate based on "was this key mentioned literally in the YAML" can be bypassed by using merge keys or aliases. Always derive security-relevant decisions from the decoded state instead (e.g., value-comparison against a snapshot of the decoded global config) — the decoded object is what the rest of the system actually sees and acts on, so it must be your source of truth.

- Before a second `yaml.Unmarshal` into the same struct (global load, then local load), a `*T` field snapshot taken from the struct **must be a value copy, never a pointer alias**. yaml.v3 reuses the existing non-nil pointee for a `*T` field on a second decode into the same struct and overwrites it in place when the second document also declares that key — an alias snapshot (`globalCleanup := cfg.Cleanup`) would therefore already hold the second document's value by the time anything compares against it, silently defeating the snapshot's purpose. `globalCleanup` in `internal/config/config.go` works around this by copying the pointee (`v := *cfg.Cleanup; globalCleanup = &v`) before the local unmarshal runs, mirroring the same pointer-reuse trap `globalKeymaps`/`cfg.Keymaps = nil` guards against (reset to nil to force a fresh allocation, since `*Keymaps` has a custom `UnmarshalYAML`) and the map analog `globalActions := maps.Clone(cfg.Actions)` guards against for the map-typed `Actions` field.
- Empirically verified raw-node shapes for a mapping-typed key like `keymaps:`, checked via `node.Kind`/`node.Tag` in a raw walk (`stampOrderAndRejectLegacy` in `internal/config/config.go`): an explicit empty block (`keymaps: {}`) decodes to a non-nil `yaml.MappingNode` with zero `Content` entries — a real declaration. A bare, `null`, or `~` value (`keymaps:` / `keymaps: null` / `keymaps: ~`) decodes to a `yaml.ScalarNode` tagged `!!null` — never a mapping, and never a declaration. A key absent from the document entirely yields no node at all (`nil`). `internal/config` treats `!!null`/absent as "unspecified" throughout (matching `mergeKeymaps`'s nil-vs-empty-map convention for table inheritance): only a real, non-null mapping node counts as a syntactic declaration. The one place that deliberately ignores the distinction is the removed-`actions:`-block rejection, which keys on the raw key's *presence* alone — a stale `actions: ~` is still a block the user should delete.

- A raw `yaml.Node` walk never expands YAML merge keys (`<<: *anchor`) or aliases; only the generic decoder does. Anything derived from such a walk therefore cannot see a key smuggled in that way, and must never be the sole gate on a security decision (see `docs/trust-model.md`). The removed-`actions:`-block rejection accepts this as a known gap: a legacy block reachable only through a merge key is silently ignored rather than rejected.
- Derived metadata that a raw-node walk stamps onto a decoded value (e.g. `Action`/`KeymapBinding`'s `Order` field, assigned from document position by `stampActionOrder`/`stampKeymapsOrder`) is silently absent — left at its zero value — for any block populated through a YAML alias or merge key, since alias/merge-key resolution bypasses the node walk that assigns it. Such a field must never participate in a value-provenance comparison (e.g. `internal/config/trust_strip.go`'s `sameShellAction`/`sameShellBinding`, which explicitly zero `Order` before comparing): including it would misclassify a genuinely global-equivalent, alias-declared value as locally differing, since its `Order` can never match a literally-declared global counterpart's stamped position.
