# Terminal Rendering & Layout

Rules for computing terminal-cell widths and handling glamour-rendered markdown in scrollable/clickable UI.

## Rules

- `lipgloss.Width()` sets *content* width; border characters are additional. When dividing total terminal width across columns (`b.Width / len(b.Columns)`), subtract border overhead per column or the total rendered width exceeds the terminal.
- Never use `len(s)` or `len([]rune(s))` for terminal layout math (hit-detection, column sizing, truncation). Use `lipgloss.Width(s)` instead — it calls `go-runewidth` internally and correctly counts CJK characters and emoji as 2 cells wide, where rune-counting undercounts them by half. Example: `handleTabClick`'s tab hit-zone math (`update.go`) was offset for any non-ASCII label until switched to `lipgloss.Width`.
- Glamour's markdown rendering adds a leading blank line to its output. When computing rendered line count for scroll-offset math, use `strings.TrimSpace(out)`, not `strings.TrimRight(out, "\n ")` — TrimRight only strips trailing whitespace and leaves the leading blank line, inflating the count.
- Glamour collapses consecutive single-newline soft breaks within a paragraph; only `\n\n` produces a hard paragraph break with a guaranteed line. When a test needs N distinct rendered lines from glamour output, join fixture lines with `"\n\n"`, not `"\n"` — single-newline fixtures render fewer lines than expected and can make scroll tests fail to exceed the visible area.
- In non-TTY test environments (e.g., `go test` in CI or headless mode), `lipgloss.ColorProfile()` auto-detects "no color support" and renders all plain `lipgloss.Style` objects as identical unstyled text, regardless of the style's actual color/attribute fields. This makes test assertions checking for style *presence* (e.g., "does the output contain prBlockedStyle.Render(glyph)?") pass trivially even if the code picked the wrong style. Fix: save the original profile with `original := lipgloss.ColorProfile()`, set `lipgloss.SetColorProfile(termenv.ANSI256)` for the test duration, and restore via `t.Cleanup(func() { lipgloss.SetColorProfile(original) })`. This forces lipgloss to render styles in the test even without a TTY, making style assertions meaningful.
- When testing rendered modal output (PR lists, milestone picker, agent list, filter modals, etc.), initialize `b.Width` and `b.Height` in the test model before asserting on rendered content width or height. `lipgloss.Width()` and layout calculations depend on these terminal dimensions being set; uninitialized zero values cause rendered content to misalign or exceed expected bounds. See helpers like `newBoardWithPRsAndExecutor` in `helpers_test.go` for the established test-model initialization pattern.
- When testing rendered output that contains variable-width prefixes (glyphs, symbols, or conditionally-rendered text), do not rely on substring assertions like `strings.Contains()` to verify column alignment — a row's "#NN" column will silently shift left/right if the prefix width varies between rows. Instead, explicitly verify alignment by extracting the prefix substring from each row and measuring its rendered width via `lipgloss.Width(row[:strings.Index(row, "#")])`, then asserting the widths are equal. Example: `pr_list_test.go`'s `TestPRList_View_ColumnAlignment_UnknownAndKnownStatusRowsMatch` uses this approach to prevent regressions where unknown-status and known-status PR rows render different prefix widths.
- When adding a user-supplied free-text field to detail-panel markdown output (e.g., title, milestone, description), wrap it with `escapeMarkdown()` to prevent glamour from misinterpreting markdown-special characters (`*`, `_`, `[`, etc.). Constrained identifiers like labels and assignee names legitimately skip escaping. Follow the established precedent in `composeDetailMarkdown` in `view.go`.
- `ansi.Strip` (charmbracelet/x/ansi) treats bare C1 bytes (0x80–0x9F) as CSI introducers and will consume the following byte if it falls in the 0x40–0x7E range, silently deleting legitimate text (e.g., `"before\x9bafter"` → `"beforefter"`). When sanitizing strings with both escape sequences and control bytes, strip the C1 range *before* calling `ansi.Strip`, not after — real ANSI sequences in user input are always ESC (0x1B, a C0 byte) prefixed, never C1-prefixed, so removing C1 first cannot break legitimate escape recognition. Order: `strings.Map` to drop C1 (0x80–0x9F) → `ansi.Strip` for escape sequences → `strings.Map` for remaining C0 (0x00–0x1F) and DEL (0x7F) control bytes, preserving `\n` and `\t`.
- `sanitizeSingleLine` is the single sanitizer for any untrusted field that must render as exactly one physical terminal line — milestone titles, card titles, PR titles, filter/assign/create-modal items, agent window/kind names, etc. It sanitizes/strips ANSI first (via `sanitizeControlSequences`), then collapses embedded `\n`/`\r`/`\t`/NEL/other Unicode whitespace runs to a single space and drops bidi/zero-width runes entirely, then trims. Apply it to the raw untrusted field BEFORE any `truncateOutput()` call — `truncateOutput` is rune-based, so sanitizing first is what makes its budget count visible characters correctly, and sanitizing after truncation risks cutting a multi-byte escape sequence or collapsible-whitespace run in half.
- Sanitize/strip ANSI before flattening or truncating, never after: `sanitizeSingleLine` strips ANSI/OSC/CSI/DCS escapes (via `sanitizeControlSequences`) first, so an escape sequence with a literal embedded newline is removed as a whole unit before any whitespace-flattening pass runs — flattening first would let the embedded newline leak a stray space and expose part of the escape sequence's payload. The corollary rule: never run this kind of sanitizer over an already-rendered ANSI segment — sanitize the raw untrusted field at its point of construction/composition, then compose/style it (e.g. `agentBadgeText` sanitizes its `agent` parameter before the `[]rune` pad/truncate, and callers must never sanitize the output of `selectedRowStyle`/`prStatusPrefix`/`agentBadgeStyle`/`formatDispatchSegment`, which would strip legitimate SGR codes). `StatusBar.SetGitStatus`/`SetDispatchStatus` are deliberately excluded from the `sanitizeSingleLine` sink itself because both receive pre-formatted segments (`formatGitSegment`/`formatDispatchSegment`) carrying legitimate SGR color codes — running `ansi.Strip` over the composed segment would strip that styling. `formatDispatchSegment`'s inputs are fully app-controlled (fixed literals + state-driven styling), so it's safe as-is. `formatGitSegment`'s `Branch` field, however, is untrusted (it comes from `git branch --show-current`, and ref names permit arbitrary non-ASCII bytes including bidi overrides and C1 controls) — it is sanitized with `sanitizeSingleLine` at its own source, inside `formatGitSegment`, before being concatenated with the ANSI-styled insert/delete/ahead/behind tokens. Only sanitize untrusted text before it is first rendered/styled, not app-controlled output that has already had styling applied — and for a mixed segment (one untrusted field + otherwise app-controlled styling), sanitize the untrusted field alone at its point of composition rather than the whole rendered string.
- An outer lipgloss style wrap does not override ANSI color escapes already emitted by an inner `Render()` call — lipgloss styles set SGR attributes but never reset ones a nested `Render()` already applied, so wrapping a pre-colored glyph string (e.g. `prStatusStyle(status).Render(symbol)`, `agentBadgeStyle(status).Render(badge)`) in a gray outer style leaves the inner color visible through the wrap. Recoloring a pre-colored glyph therefore has to happen at its own construction site (the function that picks its style), never by wrapping the already-rendered row afterward. The one case where wrapping *is* correct: plain, never-independently-colored text (row titles, text-only modal labels) — there the outer wrap is the only color applied, so it works as expected. This is why the non-selected muting convention (`selectedRowStyle`, #478) covers row text only: status glyphs built by `prStatusPrefix`/`cardStatusLines` keep their status colors on every row by design (#493), so linked PRs and live agents stay visible at a glance across the board.
- When composing `sanitizeSingleLine` with fixed-width rune truncation (e.g., `[]rune(s)[:fixedWidth]`), the semantic difference between collapsing embedded whitespace to a space vs. deleting it entirely can silently drop trailing content: `sanitizeSingleLine` replaces `\n`/`\r`/`\t`/whitespace runs with a single space to preserve word boundaries in natural language; applied to `"cla\nude"` (7 runes), it becomes `"cla ude"` (still 7 runes, the `\n` → ` `). If that result is then truncated to a fixed width (e.g., 6 runes), the trailing character is lost, yielding `"cla ud"` instead of `"claude"`. For compact identifier tokens (e.g., agent kind names, username fields) that never legitimately contain internal whitespace, deletion (not collapse) is correct — `strings.Fields` + `strings.Join(fields, "")` — because it avoids the synthetic space that would consume one rune of the fixed-width budget. Use `sanitizeSingleLine` for user-entered text fields (titles, descriptions, milestones); use bespoke deletion for compact tokens. Example: `agentBadgeText` deliberately strips whitespace entirely before the fixed-width pad/truncate to avoid losing real content that would otherwise fit.
